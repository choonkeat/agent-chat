> ## 1. Esc count — you're right, 1 is correct
>
> Code today: `terminal-ui.js:4868-4869` fires `\x1b` twice back-to-back, then types text 300ms later.
>
> **Two independent bugs.**
>
> **(a) The two Escs can merge into zero interrupts.** Same file, line 4685, maps `Alt+Left` to `\x1b b` — proof the receiving TUI parses ESC-then-byte as a *meta sequence*, using the standard ~50ms escape-delay. Two Escs written microseconds apart arrive as `ESC ESC` in one read → parsed as "Alt+Esc" (one event, usually discarded), not two Esc presses. That's your "doesn't always work".
>
> **(b) The 2nd Esc is never useful and is sometimes destructive.** Scenario matrix at the moment interrupt fires:
>
> | Claude state | 1st Esc | 2nd Esc |
> |---|---|---|
> | Working / tool in flight (incl. blocked on our `send_message`) | interrupts ✅ | now idle → opens rewind picker ❌ |
> | Idle, empty prompt | no-op | rewind picker ❌ |
> | Idle, draft text in box | clears draft | rewind picker ❌ |
> | Permission / MCQ dialog open | dismisses (= deny) | rewind picker ❌ |
> | `@`/`/` autocomplete popup open | closes popup | clears/rewind ❌ |
> | Ctrl+O expanded output / transcript view | exits view | rewind picker ❌ |
> | Vim mode, insert | → normal mode | → normal mode |
>
> In every state the **first** Esc does the useful thing. The second only ever advances one state further — and from idle that's the "jump to a previous message" rewind picker, which then eats our injected `check_messages` text as filter input and the trailing `\r` selects a rewind target. That's a silent conversation/code rollback.
>
> Vim mode is the one unfixable case (typed text becomes vim commands) — document, don't solve.
>
> **Proposed sequence:** `\x1b` → wait 300ms → `\x15` (Ctrl+U, clear input line — safe no-op when empty, no state change, replaces the 2nd Esc's only legit job) → 50ms → text → 300ms → `\r`. I'd verify Ctrl+U is bound in Claude's input before shipping it; if not, drop it and just send Esc + delay + text.
>
> ## 2. Secrets over chat — mechanic is right, one blocking gap
>
> What I verified in the code:
>
> 1. **Agent already gets paths, not bytes.** `eventbus.go:563-568` passes `f.Path` + mime + size into the check_messages text. Contents never enter the tool result. File upload is the correct mechanic.
> 2. **Blocking gap: the exporter copies *every* attachment, not just images.** `chatlogexport.go:314` (`writeEventAttachments`) copies each `e.Files[i].Path` into `agent-chats/assets/` verbatim. A secret uploaded today gets committed. Filename-based exclusion is the wrong fix — needs an explicit flag.
> 3. **Second gap: uploads are served unauthenticated** at `/uploads/<uuid8>-<name>` (`main.go:355`). A secret must not live in `uploadDir` at all.
>
> **Design (4 pieces):**
>
> 1. **Client**: 🔒 item in the paperclip menu → masked textarea, so you paste the token directly instead of first saving it to a file. POSTs to a new `/secret` endpoint.
> 2. **Server**: writes to a separate `secrets/` dir (0700, file 0600), name `secret-<uuid>` with the original filename discarded, `FileRef.Secret = true`. Not under the `/uploads/` FileServer.
> 3. **Export + UI**: `writeEventAttachments` skips `Secret` files; bubble renders `🔒 secret sent (not exported)`; path redacted in the chat log.
> 4. **Lifetime**: TTL delete (~15 min) + delete on session end. Simpler and more predictable than burn-after-read, which breaks retries.
>
> Agent-facing text would be the path plus "contains a secret — pass by path (`cmd < path`, `--token-file path`), never Read/cat it, never echo it".
>
> **Honest limit:** this guarantees *not in the chat UI, not in the export, not over HTTP*. It cannot stop the agent from `Read`-ing the file — that would put the secret in `~/.claude/projects/*.jsonl`. Only path-passing keeps it out of the transcript.
